# ML-B Pre-Experiment Report

Written before any ML-B code was executed, based on direct inspection of the repository at commit `bc2735369a2ebe420d2c7d02395edca1ca96e427` (HEAD == origin/main, working tree clean except untracked `.claude/`).

## 1. Frozen categorization candidate set (ML Spec §5)
Exactly three: (1) K-Means (current baseline, re-evaluated under corrected isolation), (2) TF-IDF + Logistic Regression, (3) TF-IDF + Linear SVM. No others permitted without a spec amendment.

## 2. Frozen forecasting candidate set (ML Spec §11)
Exactly four: (1) Naive, (2) Seasonal Naive, (3) existing Random Forest (TRD-shipped hyperparameters: `n_estimators=100, max_depth=10, min_samples_leaf=5`), (4) Ridge.

## 3. Frozen multi-step forecasting strategies (ML Spec §11.1)
Required minimum: (A) last-known-history, (B) recursive. (C) direct — only if A/B evidence warrants it.

## 4. Available datasets and provenance
- `data/raw/synthetic_24mo.csv` — 779 rows, 2023-01 to 2024-12, generated by `scripts/generate_synthetic_24mo.py`.
- `data/raw/synthetic_12mo.csv` — an earlier, shorter synthetic set (not used; the 24-month set is strictly more history for the same purpose).
- No file anywhere in the repository constitutes an independent (Tier A/B/C) categorization evaluation dataset. `data/processed/` and `data/raw/` beyond the two synthetic files above contain no transaction data.

## 5. Evidence tier of every dataset
- `synthetic_24mo.csv` / `synthetic_12mo.csv`: **Synthetic** (ML Spec §3.1).
- No Tier A, B, or C dataset existed in the repository prior to this ML-B pass.

## 6. Tier A (real/natural) data available?
**No.** Confirmed by directory inspection (`data/raw`, `data/processed`, `data/exports` contain only synthetic/generated/export content) and by the ML Spec's own §3.2 statement that no such dataset exists yet. This was surfaced to the user as a blocking decision (§24 below) before any dataset was built.

## 7. Tier B (independently curated) data available?
**No, prior to this ML-B pass.** Built during this pass: `data/evaluation/tier_b_benchmark.csv` (228 rows, 81 merchant groups, hand-authored, vocabulary independently verified non-overlapping with `pipeline/cluster.py`'s `MERCHANT_KEYWORDS`).

## 8. Tier C (public dataset) available?
Not searched/acquired. The user's explicit choice (§24) was to proceed with a hand-authored Tier B benchmark rather than search for a Tier C dataset — deferred, not ruled out for a future pass.

## 9. Existing synthetic dataset/generator and its limitations
`scripts/generate_synthetic_24mo.py` produces `synthetic_24mo.csv`. Limitation (verified, matches ML Spec §2): its merchant vocabulary is authored by the same person and shares exact substrings with `pipeline/cluster.py`'s `MERCHANT_KEYWORDS` (e.g. both use `"NETFLIX"`), which is exactly the coupling ML-B's Tier B benchmark exists to avoid for categorization. This coupling does not block using the synthetic set for *forecasting* mechanism/behavior testing (ML Spec §17), since forecasting evaluation targets the time-series model's behavior on a category-labeled input stream, not the categorization decision itself.

## 10. Existing categorization labels and how they were produced
`pipeline/cluster.py::_get_true_labels` — a fixed substring-keyword dictionary (`MERCHANT_KEYWORDS`) matched against uppercased merchant text, first match wins, unmatched defaults to `"Other"`. Confirmed by direct code reading. Per this session's explicit terminology instruction, these are called **keyword-derived (heuristic) labels**, never "pseudo-labels."

## 11. Merchant/group identifiers available for leakage-safe splitting
`synthetic_24mo.csv` has no explicit merchant-group identifier column — only free-text `Description`. The Tier B benchmark built for ML-B includes an explicit `merchant_group` column by design, specifically to support ML Spec §6's merchant-grouped splitting requirement.

## 12. Category counts and class balance
Frozen taxonomy: 8 categories (`config.CATEGORIES`), fixed by PRD §9.4, not altered by ML-B. Tier B benchmark distribution (228 rows): Food & Dining 46, Transport 35, Entertainment 29, Rent & Utilities 29, Shopping 27, Subscriptions 21, Other 21, Healthcare 20 — imbalanced but every category has ≥8 merchant groups, enough for a merchant-grouped stratified split into all three partitions.

## 13. Forecast history length and category coverage
`synthetic_24mo.csv` covers 24 unique calendar months (2023-01 through 2024-12) across all 8 categories once run through the production K-Means artifact — verified by direct computation before writing any evaluation code.

## 14. Sufficient history for required seasonal/sensitivity analyses?
- Seasonal Naive requires ≥12-13 months of history — satisfied for a meaningful (though not huge) portion of the 24-month range.
- §15 history-length sensitivity (6/9/12/18-month truncations, common origin set) requires ≥18 months of available prior history at a shared set of origins — only 3 such origins exist after reserving 3 months for the sealed final period. **Feasible but small**, disclosed as a limitation rather than blocking the whole ML-B pass (per the Failure/Blocker Rule's allowance that a secondary analysis being small doesn't block the core evaluation).

## 15. Existing V1 evaluation code that must NOT be reused blindly
`pipeline/forecast.py::walk_forward_validate`'s calendar-respecting expanding-window *style* was reused as a pattern (ML Spec §12 explicitly endorses this); its GridSearchCV path (row-sorted `TimeSeriesSplit`) was explicitly NOT reused, per the documented flaw. `pipeline/cluster.py::fit_and_evaluate`'s 160/40 internal split was explicitly NOT reused for K-Means (ML Spec §6.1 requires the outer TRAIN/VALIDATION/TEST partitions instead).

## 16. Existing production model code that ML-B must not mutate
`pipeline/cluster.py`, `pipeline/forecast.py`, `pipeline/features.py`, `pipeline/ingest.py`, `models/kmeans_model.pkl`, `models/rf_model.pkl`, `backend/services/categorization_service.py`, `backend/services/forecast_service.py` — none modified during ML-B (confirmed by final `git status`/`git diff` review, see the final handoff message).

## 18. Reproducibility strategy
- **Seeds:** 42 throughout (splitting, K-Means, RF, benchmark date/amount jitter).
- **Environment:** `requirements.txt`'s already-pinned versions (unchanged by ML-B).
- **Deterministic splitting:** `data/evaluation/tier_b_split_v1.json` freezes the merchant→partition assignment; re-running the split logic with the same seed reproduces it exactly (tested).
- **Artifact/result naming:** `reports/ml/results/*.json`/`*.csv`, one file per concern, plus `experiment_log.jsonl` (append-only per run, reset at the start of `python -m ml.run_all`).

## 19. How the FINAL UNTOUCHED TEST remains sealed throughout ML-B
See the main report's §7 for the three-layer mechanism (structural exclusion at fold/partition-construction time, a runtime assertion that halts the run on any leak, and dedicated regression tests). No code path in `ml/` computes a metric against FINAL_TEST rows or the reserved final 3 calendar months.

## 20. Blockers to executing the frozen ML Spec faithfully
**One blocking decision was surfaced and resolved before any code was written:** no independent categorization evaluation dataset existed (ML Spec §24, item 1). Presented to the user as an explicit choice (Tier B hand-authored / Tier A user-supplied / search for Tier C / stop and report); the user chose Tier B. This is not a contradiction between frozen documents — it is exactly the open acquisition question ML Spec §24 itself flags as unresolved and assigns to ML-B's own execution. No other blocker (contradiction between ML Spec/TRD/PRD/repository, or insufficient data to run the *core* required evaluation) was found. The only *secondary* limitation is history-length sensitivity's small usable-origin count (item 14 above), which the Failure/Blocker Rule explicitly permits reporting as a scoped limitation rather than halting ML-B.
