# Data pack schema

Generated by `backend/services/powerbi_export_service.py`, on demand, from
the live V2 database — every column here mirrors that module's own
`_TRANSACTION_COLUMNS`/`_CATEGORY_SUMMARY_COLUMNS`/`_PORTFOLIO_COLUMNS`/
`_FORECAST_COLUMNS` constants exactly, so this document never drifts from
what the export actually produces. If those change, update this file in the
same change.

All four files are scoped to whichever data mode is currently active in the
app (Demo or Real) — never a mix of both.

## `transactions.csv`

One row per transaction.

| Column | Type | Notes |
|---|---|---|
| `date` | Date (`YYYY-MM-DD`) | |
| `merchant` | Text | Cleaned merchant name, not the raw bank description. |
| `amount` | Decimal | |
| `bank_source` | Text | Which bank format this came from; blank for manually-added rows. |
| `category` | Text | The **effective** category — your confirmed correction if you made one, otherwise the model's prediction. Never the model's raw/advisory guess (see the app's How It Works page). |
| `is_manual_override` | True/False | Whether you personally confirmed/corrected this row's category. |

**Not included, deliberately:** the raw/untouched bank description (can
carry masked account or reference numbers) and internal matching/advisory
fields (`merchant_key`, `decision_source`, `model_category`) — none of these
are needed for a spending report, and excluding them is a privacy choice,
not an oversight.

## `category_summary.csv`

One row per (month, category) pair — the same monthly aggregation the
Dashboard's own category-breakdown and trend cards use.

| Column | Type | Notes |
|---|---|---|
| `month` | Text (`YYYY-MM`) | |
| `category` | Text | Effective category, same semantics as above. |
| `total_spend` | Decimal | Sum of `amount` for that month/category. |

## `portfolio.csv`

One row per holding.

| Column | Type | Notes |
|---|---|---|
| `ticker` | Text | |
| `shares` | Decimal | |
| `avg_cost` | Decimal, **may be blank** | Blank means cost basis was never recorded — never a fabricated 0. |
| `current_price` | Decimal, may be blank | Blank if prices have never been refreshed for this holding. |
| `current_value` | Decimal, may be blank | `shares * current_price`; blank whenever `current_price` is. |
| `pnl` | Decimal, **may be blank** | `current_value - (shares * avg_cost)`; blank whenever EITHER `avg_cost` or `current_price` is blank — never computed against a guessed cost basis. |
| `price_last_updated` | Timestamp, may be blank | The last genuine price refresh, or a demo-seed sentinel timestamp for never-refreshed demo holdings (see the app's Portfolio page, which labels this "Demo snapshot"). |

**A blank `avg_cost` or `pnl` cell is a real "unknown," not a zero.** A
Power BI measure that sums or averages these columns should exclude blanks
explicitly (Power BI's own SUM/AVERAGE already ignore blank cells by
default, which is the correct behavior here — do not replace blanks with 0
in a calculated column, or the P&L totals become fabricated).

## `forecast.csv`

One row per (category, forecast month) pair, from the most recently
generated forecast run for the active mode — empty (headers only) if no
forecast has been generated yet.

| Column | Type | Notes |
|---|---|---|
| `category` | Text | |
| `forecast_month` | Text (`YYYY-MM`) | |
| `month_offset` | Integer (1-3) | Months ahead of the forecast run. |
| `predicted_amount` | Decimal | |
| `is_available` | True/False | Whether this category had enough history to forecast at all. |
| `generated_at` | Timestamp | When this forecast run was generated. |
| `is_stale` | True/False | Whether PlainCents has since flagged this run stale (your transaction data changed after it ran). A stale forecast is still historically real — it just may no longer reflect your current data. |

## Suggested relationships

- `transactions[category]` ↔ `category_summary[category]` (many-to-one) —
  lets a category slicer filter both the transaction list and the monthly
  summary together.
- `category_summary[category]` ↔ `forecast[category]` (many-to-one) —
  compares actual monthly totals against the forecast for the same
  category.
- `portfolio` has no natural relationship to the other three tables (it is
  a separate domain from spending, exactly as inside the app itself — see
  the app's Portfolio "How your portfolio works" section) — keep it on its
  own report page rather than joining it to spending data.
